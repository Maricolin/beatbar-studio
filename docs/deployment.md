# 部署设备、性能与容量规划

本章区分代码中的硬限制、工程规划建议和实测结果。当前应用默认面向单机使用，后端负责分析和逐帧编码；浏览器负责交互与预览。下面的建议不是采购规格，也不是对任意素材的速度或峰值内存保证。

## 运行环境

| 项目     | 要求与说明                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Python   | 3.11+，建议使用独立虚拟环境，依赖见 requirements.txt                                                                                     |
| 操作系统 | 存档实测环境为 Windows 11 x64；macOS / Linux 有手动启动方式，但仍需在目标系统验证依赖和 FFmpeg 编码器                                    |
| 浏览器   | 支持 ES modules、Canvas、Audio 和 File API 的近期 Chrome / Edge；直接选择保存路径依赖浏览器 File System Access 支持，缺失时回退下载      |
| Node.js  | 日常运行不需要；开发、格式检查、AST 索引与浏览器回归需要 Node.js 22+ 和 pnpm                                                             |
| FFmpeg   | 默认由 imageio-ffmpeg 提供，无需单独安装系统命令；不同系统发行构建的编码器可用性需验证                                                   |
| GPU      | 当前检测使用 NumPy/SciPy，绘制使用 Pillow，导出调用 CPU 编码器 libx264/libvpx-vp9；没有启用 CUDA、NVENC 或其他硬件加速，独显不是运行前提 |
| 网络     | 安装依赖时需要；本地服务和资料就绪后，日常分析、导出及学习中心均无需访问 CDN                                                             |

默认只监听 `127.0.0.1:8000`。使用期间需保持服务进程运行；浏览器不是媒体处理引擎。不要把日常工作台的数据目录与回归测试目录混用。

## 硬件规划起点

这些是按 CPU 编码和并行缓冲的工程规划起点，不是经过全素材压力测试得到的最低配置。先以自己的实际片长、尺寸、FPS、图案复杂度做一轮验证，再决定是否升级设备。

| 使用情形                       | CPU / 内存规划                                           | 磁盘与操作建议                                                        |
| ------------------------------ | -------------------------------------------------------- | --------------------------------------------------------------------- |
| 跟随教程、低分辨率短片         | 2 核 / 4 线程、8 GB 内存可作为试用起点；本机实测见下节   | 使用 640×360 / 24 FPS、串行任务，关闭占内存的软件                     |
| 日常 720p / 1080p 短片         | 4 核 / 8 线程、16 GB 内存作为规划起点                    | 建议 SSD，为数据和临时成品预留至少 20 GB，再按素材与保留份数增加      |
| 较长 1080p、多图案或连续批处理 | 8 核 / 16 线程、32 GB 内存作为规划起点；仍应限制并行任务 | 建议为输入、成品和运行中的临时文件预留 50 GB 或更多，并安排清理和备份 |

额外为 Python 环境、FFmpeg、依赖下载缓存预留数 GB；开发环境还会有 node_modules 和浏览器测试配置。内存较小的设备可先降至 640×360、24 FPS、单任务；降低分辨率会同时减少像素处理和编码压力。

## 本机实测与可复现方法

测量脚本为 `scripts/benchmark-api.py`。它上传配套的 8 秒 WAV，分析一次，再依次渲染三种 640×360 / 24 FPS 输出和一种 1280×720 / 30 FPS 合成输出。脚本通过公开 HTTP API 工作，也验证了纯代码调用链。

本轮测试设备：Intel Core i3-1115G4，2 个物理核 / 4 个逻辑处理器，标称 8 GB RAM，Windows 11 x64（系统报告版本 10.0.26200）。测试素材是合成纯音频，包含 16 个标准拍点；不存在原视频解码成本。

本轮报告为 `artifacts/acceptance-20261126/api-benchmark.json`，记录于 2026-11-26T09:19:34.329954+00:00（北京时间 17:19:34）。通过独立测试数据目录的真实 HTTP 服务重新运行脚本，四份成品已下载并核对大小及容器签名。较早的 `artifacts/api-benchmark.json` 作为历史记录保留，下面使用本轮数据。

本轮单次实测：上传及波形处理 1.315 秒，拍点分析 1.864 秒，检测结果 16 拍 / 120 BPM。渲染结果如下：

| 输出模式     | 规格              | 帧数 | 渲染观察耗时 | 成品大小     |
| ------------ | ----------------- | ---- | ------------ | ------------ |
| 素材合成 MP4 | 640×360 / 24 FPS  | 192  | 2.150 秒     | 104,106 字节 |
| 绿幕 MP4     | 640×360 / 24 FPS  | 192  | 2.189 秒     | 106,358 字节 |
| 透明 WebM    | 640×360 / 24 FPS  | 192  | 3.623 秒     | 482,955 字节 |
| 素材合成 MP4 | 1280×720 / 30 FPS | 240  | 15.543 秒    | 110,519 字节 |

环境版本：Python 3.12.14、FastAPI 0.165.0、NumPy 2.5.5、Pillow 13.0.0、imageio-ffmpeg 0.8.1、httpx2 2.16.2。相同电脑上，720p 增加像素与帧数后，耗时明显增加；这些数字仅代表该次合成音频练习，不能当作真实视频或其他电脑的性能保证。

复现时先启动独立测试服务：

```powershell
$env:BEATBAR_DATA_DIR = "$PWD\artifacts\performance-data"
.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

另开终端：

```powershell
.venv\Scripts\python.exe scripts\benchmark-api.py --machine-label "填写本机 CPU、内存与系统"
```

报告和四份下载成品默认写到 artifacts，上传素材和服务端成品写入当前 BEATBAR_DATA_DIR。脚本会替换自己固定命名的基准输出文件；不要把个人作品放到这些文件名下。

统计口径：同一已启动服务、顺序提交、每种规格一次；后台任务轮询间隔 0.1 秒；渲染耗时包括排队/提交/轮询观察，不包括最终下载。不是多轮中位数，不是并发压测，也未测量整棵进程树的峰值 RAM。真实视频解码、混音、长片、复杂图片、其他后台负载和散热降频都会影响结果，不能按 8 秒结果简单推算 20 分钟任务。

## 代码中的容量上限

| 项目         | 当前边界                                                               |
| ------------ | ---------------------------------------------------------------------- |
| 上传文件     | 最大 512 MiB                                                           |
| 素材时长     | 大于 0、不超过 1200 秒，即 20 分钟                                     |
| 输入视频尺寸 | 每边不超过 8192 像素                                                   |
| 输出尺寸     | 宽、高各 64–1920 像素                                                  |
| 输出帧率     | 1–60 FPS                                                               |
| 帧预算       | 不超过 180,000 帧，且宽 × 高 × 帧数不超过 1,000,000,000,000            |
| 拍点         | 每次项目/导出最多 100,000 个                                           |
| 项目 JSON    | 请求及记录最大 20,000,000 字节；有限数值，嵌套深度有限制               |
| 分析采样     | 22,050 Hz、单声道 float32；不是按源视频所有帧整体驻留内存              |
| 工作线程     | 单进程 ThreadPoolExecutor 最多同时运行 2 个分析/导出任务，后续任务排队 |

这些是请求校验和计算预算，不等于预留好了内存或磁盘。当前没有按可用 RAM 自动降级、严格队列长度上限、磁盘配额或自动删除策略。

## 如何估算资源

- 20 分钟分析音频仅一个 float32 单声道数组约为 `22050 × 1200 × 4 = 105,840,000` 字节，约 101 MiB。解码字节、临时数组、频谱分块、浏览器和 FFmpeg 会额外占用内存，不能把这个数当峰值。
- 一帧 1920×1080 的 RGBA 像素约为 7.9 MiB，渲染与合成可能同时持有多份缓冲，编码器另有自己的内存和线程。
- 总磁盘需求至少覆盖保留的原始素材、已导出文件、运行中的临时成品和项目 JSON。码率随内容与编码设置变化，不能从时长直接保证成品大小。
- 原始上传、项目库、成品默认分别在 data/media、data/projects、data/exports；用 BEATBAR_DATA_DIR 一起搬迁。导出和项目都不会自动清理，删除项目记录也不会删除关联素材。

## 设备验收步骤

1. 运行 `python scripts/beatbar_client.py health`，确认 API 返回 ok。
2. 使用学习 WAV 完成一次分析和低分辨率合成导出，验证声音、16 拍节奏与 8 秒时长。
3. 用一段真实目标素材测试最终尺寸/FPS和音轨，观察任务耗时、系统峰值内存、CPU、温度及剩余磁盘。
4. 单任务通过后再评估并行；若响应或内存恶化，在调用方顺序提交，不直接增大线程数。
5. 停止服务后备份数据目录，重启并打开已有项目；这是部署验收的一部分。

## 作为接口服务部署的边界

后端已可通过 HTTP 独立调用，无需浏览器参与。调用流程与 Python 客户端见 [API 与代码调用](api.md)。网页上的拖动、选中、撤销等交互状态不是单独的服务端 API；程序化编辑可先生成或修改 beats/style/project JSON，再提交渲染或项目保存。

当前没有登录鉴权、租户隔离、持久任务队列和任务重启恢复。项目修订锁是单进程 RLock，不能据此直接开多个 uvicorn workers 共享同一项目目录。运行中的任务与进度在内存中；进程重启后不能用旧 job ID 继续轮询。

若要让其他设备或业务系统长期访问，应先设计鉴权、访问控制、HTTPS 反向代理、请求体/超时限制、持久队列和存储清理，再绑定可访问地址。不要直接把默认单机 API 暴露到公网。跨域浏览器调用还需要明确配置允许的 Origin；Python/服务端代码调用不依赖浏览器 CORS。
